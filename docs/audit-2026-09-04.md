# Stream Scheduler 2 — system audit, 2026-09-04

> Method: 11 read-only auditors (one per subsystem) hunting assumptions that hold on synthetic fixtures but break on real inputs/environments — the pattern behind every incident of 2026-09-02…04. Every finding was then attacked by two independent skeptics (code-truth refuter + deployment-impact judge); a completeness critic added three gap dimensions (vertical-rotation-detection, multi-machine-no-lock, settings-fade-validation). 150 agents (Claude Sonnet), 61 raw findings → 57 confirmed, 10 refuted. Nothing in the repo was modified by the audit. Full agent transcripts: session workflow wf_5ead1ba1-d9a.

## Executive summary

This app is fundamentally sound (287/287 tests pass, and the eight previously-fixed bugs stay fixed), but this audit found 57 more real problems, proven with actual code and, where possible, real class-video/slate files and the real bundled video engine — not guesses. The six most serious ("critical") problems can make a class fail to air or air broken with nobody warned in time to fix it: (1) on a Mac, clicking the ordinary red close button — the same click that just minimizes almost any other Mac app — instantly quits Stream Scheduler and kills a live class with zero confirmation; (2) removing one occurrence of a recurring weekly class silently cancels the entire series forever, not just that week; (3) if a same-day class's video arrives more than 2 minutes after the scheduled start, the class is permanently marked "missed" with no way in the app to attach the late video and go live — even though there'd still be time; (4) when an operator confirms which studio a pasted class link should go to, that confirmation is sometimes never actually saved, so the app can silently re-guess the wrong studio at air time; (5) nothing restarts the app after a Windows Update reboot or power blip, so an unattended PC can sit at a login screen while classes silently never fire; (6) stopping a broadcast almost always force-kills the video engine rather than shutting it down politely, though because nothing in the app actually waits for a graceful shutdown anyway, this one turns out to have little practical consequence today. Beyond these, real risks include: nothing stops the streaming PC from going to sleep mid-class; using the normal lead-in slate mislabels the color settings for the whole class (a proven defect, though whether it visibly washes out colors depends on the viewer's device); a same-day re-exported video swap skips the app's own file-quality check; the app can fully quit while the video engine is still running as an invisible orphan process; network hiccups get misreported as bad login credentials; the private streaming key sits as visible plain text in the computer's process list; and software updates can silently download hundreds of megabytes in the background during class time with no on-screen indicator. Most of the remaining findings are medium- or low-severity — real but narrower issues (Windows console windows popping up, a slightly-too-slow machine going unwarned, test-coverage gaps that could let a future bug slip through) that a careful operator can usually work around or that only bite in unusual setups. My recommendation: fix the six critical items first — most are small, surgical code changes — then work down the high-severity list, starting with the sleep-prevention and update-download gating fixes since those are also cheap and protect every single class.

## Recommended actions, in order

1. Stop a Mac window-close from quitting the app and killing a live broadcast: gate window-all-closed/before-quit behind a live-broadcast check and show a confirm dialog (app/main.js:164-165).
2. Fix removeEvent() so cancelling one occurrence of a repeating weekly class does not silently cancel the whole series forever (schedule/scheduler.js:379).
3. Fix the scheduleGuid bug in portal:checkLink so the studio the operator actually confirmed is the one that gets saved, not discarded (app/ipc.js:19-23).
4. Give same-day classes a real path to attach a late video and still air after the 2-minute grace window trips, instead of a permanent dead end (schedule/model.js:6, schedule/scheduler.js:292/365).
5. Add auto-launch-at-login (or at minimum a documented/monitored safeguard) so a Windows Update reboot or power blip doesn't leave the scheduler dead all day (app/main.js:43).
6. Add an Electron powerSaveBlocker while a broadcast is live so the streaming PC cannot sleep mid-class (engine/broadcast.js:120, app/main.js:164).
7. Fix the color-metadata mistagging on the slate crossfade by adding an explicit setparams=range/colorspace/primaries=bt709 step after format=yuv420p (engine/timeline.js:52).
8. Re-validate a cached video file with probe.js whenever video-cache.js detects it changed on the drive, instead of letting an unvalidated re-export reach ffmpeg (schedule/scheduler.js:149, store/video-cache.js:107-118).
9. Make app quit actually wait for the video engine to finish stopping instead of letting Electron exit while ffmpeg is still running as an orphan (app/main.js:164, schedule/scheduler.js:430-435).
10. Add an OS-level notification (and ideally window-flash) when a class fails or is missed, since right now nothing alerts anyone who isn't already staring at the app window (renderer/app.js:262).
11. Add a real RTMPS/Mux ingest reachability check to the periodic health check, since today "Connections OK" only proves the content portal's website login works, not that any studio's stream destination is reachable (store/health.js:31).
12. Gate the auto-updater's background download (not just the install step) on live/imminent-broadcast state, and stop hiding the progress bar during a multi-hundred-MB download (app/main.js:109, renderer/app.js:193-215).

## Findings by theme

### A. Scheduler state & operator control
These bugs live in the class-scheduling logic itself (schedule/scheduler.js, schedule/model.js, app/ipc.js) and are hit through completely ordinary operator actions — not edge cases.

- **Removing one weekly occurrence cancels the whole series** (schedule/scheduler.js:379). `removeEvent()` deletes the event and persists, but never calls `renew()`, which is the only thing that ever creates next week's occurrence. Live-reproduced: removing one pending `repeatWeekly` event leaves `getEvents()` empty. *Fix:* call `renew(ev)` before removal, or give the UI an explicit "skip this week" vs. "cancel the series" choice. *Verify:* schedule one repeating class, remove it, confirm a next occurrence is (or isn't) queued as intended.
- **2-minute grace window is an unrecoverable dead end** (schedule/model.js:6, GRACE_MS = 2 min). If a `needsVideo` slot's video isn't attached within 2 minutes of its scheduled start, it's marked "missed" — and afterward neither `updateEvent()` nor `retryEvent()` will accept a late-arriving video, even though the class window may still be open. Live-reproduced: both calls fail post-grace with "Only upcoming broadcasts can be changed" / "This class has no video file yet." Also note: this is coded as a non-failure, so no warning banner appears — an operator only discovers it by opening Past Events. *Fix:* widen the window or let a `needsVideo` slot be filled and go live (at a seek offset) any time up to `fireAt+durationSec`. *Verify:* attach a video 5 minutes late to a needsVideo event and confirm it's rejected today.
- **Confirmed studio pick discarded** (app/ipc.js:19). `portal:checkLink` returns `ids.scheduleGuid` (parsed from the raw pasted link, always `''` for a plain class link) instead of `res.picked.scheduleGuid` (what was actually resolved and shown to the operator). Live-reproduced with a mocked multi-occurrence resolution: UI shows "Studio 2 (evening)," saved `scheduleGuid` is `''`. At air time the app blindly re-picks an occurrence from wall-clock time alone. *Fix:* prefer `res.picked.scheduleGuid` over `ids.scheduleGuid` when the link itself carried none. *Verify:* integration test wiring the real `portal/client.js` resolver to `app/ipc.js` with two same-day occurrences and a bare (non-broadcast-URL) link.
- **Mac red-button close kills a live broadcast, no confirmation** (app/main.js:165, schedule/scheduler.js:430). `window-all-closed`→`app.quit()`→`before-quit`→`scheduler.shutdown()` runs with zero check for a live class and no dialog, unlike the update-install path which *does* gate on `isSafeToUpdate()`. *Fix:* gate quit the same way updates already are, and confirm before killing a live class. *Verify:* read app/main.js:160-166 — no confirmation path exists.
- **No auto-start after a reboot** (app/main.js:43). No `setLoginItemSettings`/Windows Task Scheduler entry anywhere in the repo. A forced Windows Update restart leaves the scheduler dead with no process alive to fire any class, and no warning until a human relaunches the app. *Fix:* register a login item (ideally hidden/tray-based). *Verify:* reboot a real install and confirm the app doesn't relaunch itself.
- **Neither quit nor crash recovery tells the portal a broadcast ended** (schedule/scheduler.js:34, 430). A force-quit or crash mid-class leaves the portal's own "studio is live" flag stuck, though nothing locally blocks the next class from starting. Low real-world urgency; a bookkeeping gap for the content-team's own dashboard. *Fix:* fire-and-forget an `endPortal(ev)` call from both paths.

### B. Broadcast process, shutdown & sleep
- **stop() reliably SIGKILLs ffmpeg instead of a graceful stop** (engine/broadcast.js:228). Measured against the real class/slate files: graceful shutdown needs 7-15s, but the 3000ms SIGKILL timer always wins once past the slate. However, none of the three real callers (`takeover`, `stopActive`, `shutdown`) await the result anyway, so this doesn't currently change any observable app behavior — it's a real latent inefficiency, not an active bug. *Fix:* raise the grace period or start it earlier.
- **Nothing prevents OS sleep mid-class** (app/main.js:164 / engine/broadcast.js:120). No `powerSaveBlocker` call exists anywhere in the repo, confirmed by a full-repo search. An unattended machine's default sleep timer can silently kill a live class with no one there to notice. *Fix:* `powerSaveBlocker.start('prevent-app-suspension')` while live, `stop()` when done. This is duplicated across two audit passes — one fix covers both.
- **App quit doesn't wait for ffmpeg to actually exit** (app/main.js:164). `before-quit` doesn't capture the event or await `shutdown()`'s async stop. Directly demonstrated: a non-detached child process survives `process.exit()` of its parent. Combined with finding above (stop() taking up to 15s), the app's process can exit while ffmpeg is still streaming, orphaned, with no one able to stop or monitor it. *Fix:* capture the quit event, `preventDefault()`, await the real stop, then re-quit.
- **ffmpeg spawned without windowsHide** (engine/broadcast.js:125). On the real Windows 11 machines, a console window pops up on every start/retry/resume. A confused operator closing it could kill the stream outside the app's normal error handling. *Fix:* add `windowsHide: true` — a one-line change.
- **Stall-watchdog message reports the configured timeout, not the real freeze duration** (engine/broadcast.js:218) — cosmetic; doesn't change app behavior, just makes post-incident log review slightly misleading.
- **"Playing" only proves local handoff, not real receipt** (engine/broadcast.js:187) — a narrow, largely self-correcting timing window before the existing 20s stall watchdog and 30s slow-speed check would catch a real problem.

### C. Video/audio encode correctness (ffmpeg inputs)
- **Slate crossfade mistags the whole class's color metadata** (engine/timeline.js:52). Proven with the real slate JPEG and real class file through the bundled ffmpeg: with a slate, the *entire* output stream (including 100% real footage after the crossfade) is tagged full-range/BT.470bg (legacy SD) instead of the class's real limited-range BT.709 (HD) — every class that uses the normal lead-in slate. Whether viewers actually see wrong colors depends on how Mux/players honor the tag. *Fix:* append `setparams=range=tv:color_primaries=bt709:colorspace=bt709:color_trc=bt709` after the existing `format=yuv420p`; confirmed working in a live test.
- **probe.js's file validation never re-runs** (schedule/scheduler.js:149). The one-time "does this video have audio / is it playable" check only runs at manual file-pick time; a same-day re-export under the same filename (which video-cache.js explicitly detects and silently re-copies) reaches ffmpeg completely unvalidated, producing a generic, misleading "check the file and the network drive" error instead of the specific diagnosis probe.js was built to give. *Fix:* re-run `probeFile()` whenever video-cache.js detects a changed source.
- **No detection of a broadcast decoding to black/silent/garbled frames** (engine/timeline.js:26). Every monitoring signal in the app is pure timing (`out_time_us`, `speed=`); nothing inspects actual pixel/audio content. A corrupted mid-file glitch would show as a perfectly healthy "On air" status. *Fix:* add ffmpeg's blackdetect/silencedetect filters.
- **Transparent-background PNG slate leaks garbage color** (engine/timeline.js:22) — proven with a synthetic RGBA fixture; only matters if a PNG-with-alpha slate is ever chosen (today's real slates are JPEG, which has no alpha, so this is currently dormant).
- **Video orientation read from coded, pre-rotation dimensions** (engine/probe.js:32) — proven with a rotation-tagged fixture; the app airs a rotation-tagged phone video pillarboxed with the wrong slate. Only reachable via the manual "pick a video file" flow, not the normal portal-driven studio workflow.
- **Negative custom bitrate accepted and misdiagnosed** (renderer/app.js:449) — proven end-to-end with the real ffmpeg binary; a mistyped Setup value produces a "check the studio/network" error instead of pointing at the actual Settings mistake.
- **Hardcoded fps:30 vs. real 29.97fps source** (schedule/scheduler.js:154) — real but harmless: produces one duplicated frame roughly every 33 seconds, the same standard trick professional tools use for this exact conversion.

### D. Health checks & alerting
- **Health check never actually tests a studio's Mux ingest** (store/health.js:31). All four checks (engine/portal/slate/videos) can be green while every `rtmps://` studio destination is completely unreachable — the same blind spot behind the earlier macOS OpenSSL CA-bundle incident. *Fix:* add a lightweight TLS/RTMP-connect probe for stations with classes scheduled soon.
- **No alerting outside the app window itself** (renderer/app.js:262). No OS notification, sound, or window-flash exists anywhere for a failed/missed class — only an in-page banner that requires someone to already be looking at the window. On the documented unattended-kiosk deployment, a 6am failure can go unnoticed for hours. *Fix:* `new Notification(...)` + `win.flashFrame(true)` on a failed/missed outcome.
- **Health check's own file probes can starve the video-cache's I/O** (app/main.js:8). `fileReachable()` fires unbounded concurrent `fs.stat()` calls with no serialization, unlike video-cache.js's own deliberately-serialized lane built to avoid exactly this hazard on a flaky network mount. Could delay same-day pre-caching during a genuinely stuck drive. *Fix:* route health.js's file checks through the same serial lane video-cache.js already uses.
- **Slate-file health check bypasses the cache** (store/health.js:42), unlike the video check, which is cache-aware — can produce a false "network drive down" alarm even when a class would air fine off the local slate copy.
- **Crash-recovery alert can be lost to a startup race** (renderer/app.js:260) — the "a class didn't air" banner is timestamped in the main process before the renderer's own session-start clock, so on essentially every real crash-recovery launch the banner is silently skipped (the event is still correctly recorded in Past Events, just without the pop-up).
- **Health checks have no live-broadcast awareness** (store/health.js:68) and **no "is another machine already live here" check** (store/health.js:61) — both real design gaps, but the actual work each check does is too light (a version check, a few file stats) to meaningfully affect a live class in practice.

### E. Portal integration & secrets
- **Network/TLS failures reported as "check your password"** (portal/client.js:44). Any network exception (timeout, DNS, TLS handshake failure) is lumped in with a real 401/bad-credentials response and shown as "check the email and password in Setup" — exactly the kind of wrong-direction diagnosis that already cost real air time once (the Mac CA-bundle bug). *Fix:* distinguish network/timeout (status 0) from real auth rejection (4xx/5xx).
- **Mux stream key sits in plaintext in the OS process list** (engine/timeline.js:69). Proven live: the full key is visible via `ps`/Task Manager for the entire class, and (on Windows) a console window may additionally flash it on screen since spawn() omits `windowsHide`. Anyone with machine access or endpoint-monitoring (common on managed corporate fleets) can read it. *Fix:* add `windowsHide: true` as a cheap partial mitigation; consider a local relay to fully eliminate the process-argv exposure.
- **Setup screen never shows whether a password is already saved** (renderer/app.js:440). `secret:hasPassword` is wired end-to-end but never called; the password field always looks blank, so an operator revisiting Setup for an unrelated reason can accidentally overwrite a working credential with a mistyped one. *Fix:* call `secret:hasPassword` and show a "saved — leave blank to keep it" placeholder.
- **Login reports success without a real session** (portal/client.js:47) — a 2xx `/auth` response with no token is treated as `ok:true`; the real portal-provided error text is discarded, so a real login problem (expired password, MFA) surfaces later as an unrelated, generic error.
- **Station missing a secure ingest URL streams the key over plaintext** (portal/stations.js:17) — falls back to `rtmp://` silently with no warning if a station's portal record is missing its secure URL; needs an unusual portal data gap to trigger.
- **Portal API key stored and shown in plaintext** (store/settings.js:23), unlike the password, which is properly encrypted via the OS keychain. Confirmed twice across two audit passes: it's both in an unencrypted settings.json and in a plain (unmasked) text field in Setup. Not enough alone to log in, but inconsistent with the app's own stated secrecy standard.
- **No ownership check before going live** (schedule/scheduler.js:262) and **ending a broadcast affects any machine's live session** (schedule/scheduler.js:119) — if two machines are ever configured for the same class/studio at once (e.g. a leftover backup PC), nothing detects or prevents a collision, and one machine's normal "end of class" can silently kill the other's live stream. Requires an unusual multi-machine setup mistake to trigger; not how these studios are described as being deployed today.
- **Neither app-quit nor crash recovery notifies the portal a broadcast ended** — see Scheduler section above; low urgency (portal-side bookkeeping only).

### F. Local video/media cache
- **A transient file lock (e.g. antivirus) during finalize discards a fully-copied video** (store/video-cache.js:144). Proven with a fault-injection repro: `fs.renameSync()` throwing once causes the *entire, already-verified* copy to be deleted, and the class then falls back to slow exponential-backoff retries — real, but the app already falls back to streaming off the network drive in the meantime, so the practical impact is wasted time/bandwidth, not usually a missed class.
- **Same video scheduled twice is cached and stored twice** (schedule/scheduler.js:77) — class-video cache entries are keyed by event id (not by source file path, unlike slate files), so a "First Play + Replay" of the identical file wastes half the cache budget storing the same bytes twice.
- **No pending-class visibility into cache status** (schedule/model.js:9) — an operator has no way to see, ahead of time, whether an upcoming class's video is safely cached locally or still depends on the network drive; only discoverable once the class is already live (where it does report honestly).
- **onEnded() claims the portal-side stream officially ended even when that call failed** (schedule/scheduler.js:191) — the local video did stop correctly; this is a status-text mismatch with the portal's own dashboard, not an on-air failure.

### G. Update & build supply chain
- **Update download is unthrottled, ungated, and hidden from the operator** (app/main.js:109). `autoDownload=true` with no link to live/imminent broadcast state, and the renderer's own comment says the update bar stays hidden "silent through checking/downloading" — so a 165-330MB background download can compete for bandwidth with a live class with zero on-screen indication of why. *Fix:* gate the download itself (not just install) on live-broadcast state, the same way video-cache.js already gates on drive contention.
- **No periodic re-check or manual "check for updates" button** (app/main.js:157) — updates are only checked once, at launch; a machine left running for weeks (this app's normal usage pattern, given weekly class renewal) can stay on a known-broken version until someone happens to restart it.
- **Windows updates aren't code-signed, so the signature check is a silent no-op** (package.json:96) — already flagged as a known future step in the project's own docs/SIGNING.md; only becomes a real risk if the release-publishing GitHub account itself were ever compromised.
- **release-mac.sh can print "Done" even if signing verification failed** (scripts/release-mac.sh:35) — the verification step's exit code is discarded with `|| true`; most real failures already stop the script earlier, so this is a smaller residual risk.
- **FFmpeg resolver can silently fall back to an unpinned system binary** (engine/ffmpeg.js:12) — if the bundled, sha256-pinned ffmpeg ever becomes unreadable, the app quietly runs whatever Homebrew/system ffmpeg it finds instead, with no log line and a health check that still reports green.
- **CI workflow pins GitHub Actions to mutable tags, not commit hashes** (.github/workflows/windows-installer.yml:29) — standard hygiene; the specific actions used (checkout, setup-node) have no history of compromise.

### H. Platform specifics (Windows / Mac)
- **Per-user Windows install + per-user roaming schedule data** (package.json:97) — a second Windows login on the same shared studio PC sees no app or an empty schedule, with nothing explaining why. Only matters if a PC is ever genuinely shared across logins.
- **Windows install is unsigned, triggering a SmartScreen warning** (docs/SIGNING.md:48) — a known, already-documented gap; a one-click "Run anyway" for the operator, not a broken install.
- **Rolling log file lives in the Windows Roaming profile** (app/main.js:61) — contradicts the app's own stated policy of keeping bulk/growing data out of the roaming profile, but capped at ~4MB so the real-world cost (slower logon sync on a domain-joined PC) is minor.
- **Single-instance lock gives false confidence** (app/main.js:43) — Electron's lock only covers one Windows login on one machine; it does nothing for the two-PCs-per-studio or two-logins-on-one-PC scenarios described elsewhere in this report.

### I. Test coverage gaps (not currently causing failures, but reduce future confidence)
- **All 287 tests use synthetic video** (scripts/make-fixtures.sh:8) — no HEVC, no 4:4:4 slate, no chunked video/audio-interleave pattern anywhere in the suite, which is exactly the shape of input that caused two of the eight already-fixed incidents. A committable 20-second real-input fixture was proven feasible in this audit.
- **The one real-ffmpeg pacing test never checks pacing stays near 1.0x** (test/encode-speed.test.js:68) — a future pacing regression (like the already-fixed -re bug) could pass all 287 tests; the app's own live speed-warning would likely still catch it in production, but not before a class was already affected.
- **The only pacing/AV-sync rehearsal harnesses aren't run in CI or before a release** (scripts/rehearsal-pacing.js:8) — they require a manually-installed dependency (mediamtx) that isn't present in CI or documented in the release checklist.

slate accepted by the health check; "Show the log file" button; GitHub Actions

## Cannot be fixed in code — decisions or purchases for the owner
- **Windows installer is unsigned** (SmartScreen warning on first install).
  Needs a Windows code-signing certificate (an annual purchase). Until then the
  warning is expected and the "More info → Run anyway" path is normal.
- **Two machines can stream the same class.** Any real guard needs a lock the
  studios share (a portal field or a shared file). Today this is procedural:
  one machine per studio schedule. The app cannot detect a sibling.
- **Per-user Windows install / per-user schedule.** A second Windows login sees
  its own empty schedule. Moving the schedule to a machine-wide location is a
  data migration with its own risks; the safer rule is one Windows account per
  streaming PC.
- **"Playing" cannot prove the studio received the stream.** RTMP gives no
  such acknowledgement; the ingest probe and the black/silent detection are the
  closest available proxies, and both are now in place.
- **Rehearsal harnesses need `mediamtx`** (a local RTMP server) and so cannot
  run in CI. They remain manual pre-release tools.
